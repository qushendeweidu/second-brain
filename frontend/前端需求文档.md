## 1. 系统概述

大众商城（DAZHONG MALL）是面向大众消费者的综合电商平台。后端工程命名为 `second-brain`，这只是工程名，产品**不是**"第二大脑/笔记"类应用。当前后端已完成**用户体系 + 权限管理 + 个人资料 + 第三方身份绑定（GitHub）**；商城业务模块（商品、购物车、订单）**尚无后端接口**（`ShopController` 为空壳，`Goods` 实体未启用），前端本期不实现商品类页面，待后端接口就绪后再迭代。

| 模块 | 说明 | 主要使用者 |
|---|---|---|
| 认证 | 登录 / 注册 / 短 token 换取 | 所有用户 |
| 用户管理 | 用户增删改查、分页筛选 | 管理员 ADMIN |
| 角色权限 | 角色与权限的查看、更新、删除 | 管理员 ADMIN |
| 个人资料 | 昵称 / 邮箱 / 电话 / 头像 / 简介 | 登录用户（本人）+ 管理员 |
| 账户管控 | 封禁、删除登录态、请求限流 | 管理员 ADMIN |
| 第三方绑定 | GitHub OAuth 绑定 / 解绑 | 登录用户 |
| 商城业务（规划中） | 商品、购物车、订单 | 暂无后端接口，本期不做 |

### 2.4 认证与鉴权设计（核心，务必先读）

后端采用**双 token** 机制，命名容易混淆，先记住这张表：

| 概念 | 后端称呼 | **请求头名称** | 有效期 | 密钥 | 携带内容 |
|---|---|---|---|---|---|
| 长 token | refresh | **`RefreshToken`** | 30 天 | JWT_SECRET | `sub=userId`、`roles[]`、`permissions[]`、`iss=second-brain` |
| 短 token | generation | **`Authorization`** | 1 小时 | **长 token 本身**（HS） | 仅 `sub=userId`、`iss`、`exp` |

> ⚠️ **反直觉提醒**：`Authorization` 头里放的是**短 token**（1 小时、不含权限）；`RefreshToken` 头里放的是**长 token**（30 天、含权限）。短 token 的签名密钥就是长 token 字符串，二者必须配对使用。对应后端配置：`token.refresh=RefreshToken`、`token.generation=Authorization`。

**前端必须遵守的规则：**

1. **除白名单接口外，每个请求都必须同时携带 `Authorization` 与 `RefreshToken` 两个请求头**，缺任一 → 401 无效 token。
2. **登录响应的 `data` 是一个 Map**，key 就是请求头名，前端应把 `data` 原样存为 `{ header名: token值 }`（详见 3.2.1）。例如返回 `{"RefreshToken":"eyJ...(长token)","Authorization":"eyJ...(短token)"}`，则按键名对应存两个 token；**可能只返回其中一个**（当请求头已带有效 token 时后端不重复签发）。
3. 后端会在 Redis 校验长 token 与 `user:{userId}:key` 一致；改角色/删角色/删用户/封禁会删除该 key，导致旧 token 立即失效，**前端收到 401/40101/40102 时应清空本地 token 并跳登录**。
4. 登录后可从长 token 的 `roles`/`permissions` claim（base64 解 payload 即得）或调用管理接口获取用户权限，用于前端路由与按钮级控制。

**token 存取建议：**

- 长 token（30 天）：`localStorage` 持久化。
- 短 token（1 小时）：可存内存 + 页面刷新时调用 `POST /user/get_short_token`（白名单接口）用长 token 换取新短 token。
- 写入统一封装：`token.ts` 提供 `getTokens() / setTokens(map) / clearTokens()`。

**请求拦截器：**

```ts
request.interceptors.request.use((config) => {
  const { Authorization, RefreshToken } = getTokens();
  if (Authorization) config.headers.Authorization = Authorization;
  if (RefreshToken) config.headers.RefreshToken = RefreshToken;
  return config;
});
```

**响应拦截器：**

```ts
// 统一以 body.code 判断业务成败（200=成功），不要依赖 HTTP 状态码
response => {
  if (res.code === 200) return res.data;
  // 40101/40102/401/40103/40104 → 清 token 跳登录
  // 其余 → 全局错误提示（msg 即后端文案）
  return Promise.reject(new Error(res.msg));
}
```

### 2.5 统一响应结构 `R<T>`

所有接口响应体：

```json
{
  "code": 200,
  "msg": "成功",
  "data": {}
}
```

- `code=200` 成功；其余为业务错误码（见 3.1.2 错误码表）。
- 前端**以 `code` 为准**判断成功/失败，`msg` 可直接展示给用户。
- 认证失败的 HTTP 状态码可能不是 200，但仍返回上述 JSON 结构。

### 2.6 分页约定

- 请求：分页参数放在查询 DTO 的 `pageDTO` 子对象：`{ pageDTO: { pageNum, pageSize } }`。
- 默认值：`pageNum=1`、`pageSize=10`；**范围 1~100，超出回退默认值**。
- 响应：

```json
{
  "code": 200,
  "msg": "成功",
  "data": {
    "records": [],
    "total": 0,
    "pageNum": 1,
    "pageSize": 10,
    "pages": 0
  }
}
```

### 2.7 时间格式约定

- **后端输出**：`yyyy-MM-dd HH:mm:ss`（LocalDateTime 全局序列化格式）。
- **后端入参兼容**：`yyyy-MM-dd HH:mm:ss`、`yyyy-M-d HH:mm:ss`、`yyyy-M-d H:m:s`、ISO-8601 四种格式均可解析。
- 前端筛选时间范围参数（如 `userCreateStartTime`）传字符串即可。

### 2.8 静态资源访问

- 路径 `/file/**` 由后端直接代理到 MinIO（`fileHost/bucketName`），**公开可访问、无需 token**。
- 头像等文件上传后返回的 URL（如 `/file/xxx.png`）可直接作为 `<img src>` 使用。
- 该路径在后端白名单内，不会被 JWT 过滤器拦截。

### 2.9 权限模型与前端权限控制

- 角色：`ADMIN` / `USER` / `GUEST`（种子数据示例，实际以数据库为准）。
- 权限：字符串列表，如 `user:add`、`user:update`、`user:delete`、`note:add`、`note:update`、`note:delete`、`user:read`。
- 后端鉴权：`@PreAuthorize`（`hasRole('ADMIN')` 等），权限来源于**长 token**。
- 前端实现：
  - 路由守卫：非登录态 → 登录页；ADMIN 专属页面校验 `roles` 含 `ADMIN`。
  - 按钮级：封装 `v-permission` 指令 / `<Permission>` 组件，依据 `permissions` 数组控制（如"新增用户"需 `user:add`）。
  - **改权限后用户会被强制重登**（后端删除 Redis key），前端对 401 的兜底跳登录天然兼容。

### 2.10 页面功能清单

**游客/登录相关**
- 登录页：用户名 + 密码。
- 注册页：用户名 + 密码（密码至少 6 位）。

**个人中心（登录用户）**
- 查看本人资料：昵称、邮箱、电话、头像、简介。
- 编辑资料：昵称/邮箱/电话/简介（注意 2.11 的表单编码坑）。
- 上传/更换头像。
- GitHub 绑定 / 解绑（流程见 3.7）。

**管理后台（ADMIN）**
- 用户列表：分页 + 多条件筛选（用户名、昵称、邮箱、电话、简介模糊、状态、角色、权限、创建/更新时间范围）。
- 用户详情查看（含资料与角色权限）。
- 创建用户、编辑用户（含资料与简介）、删除用户。
- 角色权限查看 / 编辑 / 删除（编辑后用户强制重登）。
- 封禁 / 解封（临时封禁、永久封禁）、删除用户登录态。
- 请求限流（按 restrictId 配置对用户限流）。

### 2.11 特殊接口注意事项（联调前必看）

| 接口 | 坑点 | 前端应对 |
|---|---|---|
| `PATCH /user/updateUserProfile` | 方法参数**没有 `@RequestBody`**，Spring 按表单/query 绑定，传 JSON body 会绑不上 | 用 `application/x-www-form-urlencoded`（`URLSearchParams`）或 query 参数传递 `userId/nickName/email/phone/bio/avatar`；或联系后端补 `@RequestBody` 后改回 JSON |
| `POST /user/saveUserAvatar` | `userId` 是 **query 参数**，文件是 `multipart` 字段 **`multipartFile`**（与后端方法参数同名，不是 `file`） | `FormData` 追加 `multipartFile`，URL 上带 `?userId=xxx`；同时带两个 token 头 |
| `POST /user/login` | 响应 `data` 的 key 即请求头名，且可能缺其一 | 把 `data` 直接当 `{header:token}` 存入；不要硬编码 key 名 |
| `GET /auth/github/authorize` | 返回**裸 URL 字符串**，不是 `R` 包装 | 直接 `window.open(url)` 或跳转；不要按 R 结构解析 |
| `POST /auth/github/callback`、`DELETE /auth/github/unbind` | 返回 void（无 body） | 成功即 200；失败会返回 R 错误结构，按错误码提示 |
| `POST /user/get_short_token` | 白名单接口，但需要带长 token | 在请求拦截器里对白名单也放行携带 token（无 token 时该接口会失败） |
| GitHub 模块 | 已实现 `/auth/github` 三接口（authorize / callback / unbind），用于绑定当前登录用户的 GitHub 身份 | 按 3.7 对接；`authorize` 返回裸 URL、`callback`/`unbind` 返回空 body |

### 3.2 认证模块

#### 3.2.1 登录 `POST /user/login`

- 鉴权：白名单（无需 token）
- Content-Type：`application/json`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| username | string | ✅ | 用户名 |
| password | string | ✅ | 密码（BCrypt 校验） |

请求示例：

```json
{ "username": "admin", "password": "123456" }
```

响应示例：

```json
{
  "code": 200,
  "msg": "成功",
  "data": {
    "RefreshToken": "eyJhbGciOiJIUzI1NiJ9...（长token，30天）",
    "Authorization": "eyJhbGciOiJIUzI1NiJ9...（短token，1小时）"
  }
}
```

> 说明：
> - `data` 的 **key 即请求头名**，把整个 `data` 存入本地（`setTokens(data)`）。
> - 若请求头已携带有效 token，后端只返回缺失的那个（可能只有 `Authorization` 或只有 `RefreshToken`）。
> - 用户被永久封禁（`status=0`）或临时封禁（Redis key 为 `"0"`）时登录被拒，返回 `40207`。

**常见错误**：`40203` 用户不存在、`40204` 密码错误、`40207` 账户已被封禁。

#### 3.2.2 注册 `POST /user/register`

- 鉴权：白名单（无需 token）
- Content-Type：`application/json`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| username | string | ✅ | 用户名（唯一） |
| password | string | ✅ | 密码（后端不做最小长度强校验，建议前端至少 6 位） |

请求示例：

```json
{ "username": "wangwu", "password": "abc123" }
```

响应示例：

```json
{ "code": 200, "msg": "成功", "data": null }
```

> 说明：注册即创建用户，默认 `status=1`，默认角色 `["USER"]`、权限 `["user:read"]`，资料表默认简介 `"这个人很懒，什么都没有留下"`。**注册成功不会自动登录**，前端需跳登录页。

**常见错误**：`40211` 账户名重复。

#### 3.2.3 获取短 token `POST /user/get_short_token`

- 鉴权：白名单接口，但**必须携带 `RefreshToken` 长 token**
- 无 body

响应示例：

```json
{ "code": 200, "msg": "成功", "data": "eyJhbGciOiJIUzI1NiJ9...（短token）" }
```

> 说明：前端刷新页面后用长 token 换取新的短 token，把 `data`（短 token）存为 `Authorization` 头。用户不存在/被封禁/短时封禁时返回 `401`/`40207`。

### 3.3 用户管理（全部要求 ADMIN）

> 通用：以下接口均需同时携带 `Authorization` + `RefreshToken`，且长 token 中 roles 含 `ADMIN`，否则返回 `40103`。

#### 3.3.1 创建用户 `POST /user/create`

- 鉴权：ADMIN
- Content-Type：`application/json`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| username | string | ✅ | 用户名，≤255，唯一 |
| password | string | ✅ | 密码，6~255 位 |
| nickName | string | ❌ | 昵称，≤255 |
| email | string | ❌ | 邮箱，格式校验，≤255 |
| phone | string | ❌ | 电话，≤255 |
| bio | string | ❌ | 简介，≤255；为空默认"这个人很懒，什么都没有留下" |
| status | integer | ❌ | 1 正常 / 0 禁用，默认 1 |

响应：

```json
{ "code": 200, "msg": "成功", "data": 4 }
```

> `data` 为新用户 id。**常见错误**：`40211` 用户名重复。

#### 3.3.2 删除用户 `DELETE /user/{id}`

- 鉴权：ADMIN

### 3.6 账户管控（全部要求 ADMIN）

#### 3.6.1 封禁用户 `POST /user/blockedUser`

- Content-Type：`application/json`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| userId | long | ✅ | 目标用户 |
| blockedTime | long | ✅ | 封禁时长数值（0 及以上） |
| timeUnit | string(枚举) | ✅ | 时间单位：`NANOSECONDS`/`MICROSECONDS`/`MILLISECONDS`/`SECONDS`/`MINUTES`/`HOURS`/`DAYS`，常用 `SECONDS`/`MINUTES`/`DAYS` |
| blocked | boolean | ✅ | 是否永久封禁（true 时置 `user.status=0`） |

请求示例（临时封禁 30 分钟）：

```json
{ "userId": 2, "blockedTime": 30, "timeUnit": "MINUTES", "blocked": false }
```

响应：

```json
{ "code": 200, "msg": "成功", "data": null }
```

> 行为说明：
> - `blockedTime` 非空 → Redis 写入 `"0"` 封禁标记，TTL = `blockedTime × timeUnit`，到期自动解除；期间所有携带该用户 token 的请求返回 `40207`。
> - `blocked=true` → 同时将 `user.status` 置 0（永久封禁）并删除 Redis 登录态。
> - **解封**：临时封禁等 TTL 过期即可；永久封禁需先用 `PATCH /user/update` 将 `status` 改回 1，再调用 `DELETE /user/deleteUserSecurity/{userId}` 清理残留 key（或等待登录）。

#### 3.6.2 删除用户登录态 `DELETE /user/deleteUserSecurity/{userId}`

- 作用：删除 `user:{userId}:key`，该用户所有已签发 token 立即失效（强制重登）；也可用于"解除临时封禁"。
- 响应：`{ "code": 200, "msg": "成功", "data": null }`

#### 3.6.3 用户限流 `POST /user/restrictUserToken`

- 参数均为 **query 参数**：`userId`、`restrictId`、`timeUnit`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| userId | long | ✅ | 被限流用户 |
| restrictId | long | ✅ | 限流配置 id（种子数据 `1` = 100 次 / 60 秒） |
| timeUnit | 枚举 | ✅ | 时间单位，决定窗口换算（同 3.6.1） |

请求示例：

```
POST /user/restrictUserToken?userId=2&restrictId=1&timeUnit=SECONDS
```

响应：

```json
{ "code": 200, "msg": "成功", "data": null }
```

> 说明：按 `user_restrict` 配置（`restrictRequest` 次 / `windowSecond` 秒窗口）对用户进行限流，窗口内超限返回 `40208 用户已被限流`。

### 3.7 GitHub 第三方身份绑定

> 说明：GitHub 绑定模块已实现（authorize / callback / unbind），用于给**当前登录用户**绑定 GitHub 身份；不是"用 GitHub 直接登录"的入口（后者暂无接口）。

#### 3.7.1 获取 GitHub 授权地址 `GET /auth/github/authorize`

- 鉴权：需要登录（从 `RefreshToken` 长 token 解析 userId，生成一次性 state/verifier 存 Redis，5 分钟有效）
- ⚠️ 返回**裸 URL 字符串**（非 `R` 包装）

响应：

```
https://github.com/login/oauth/authorize?client_id=xxx&redirect_uri=xxx&state=xxx&code_challenge=xxx&code_challenge_method=S256
```

前端流程：

1. 点击"绑定 GitHub" → 请求本接口拿到 URL → `window.location.href = url` 或 `window.open(url)`。
2. 用户在 GitHub 授权后，GitHub 302 跳回 `redirect_uri`（前端回调页），URL 带 `code` 与 `state` 参数。
3. 前端回调页读取 `code`、`state` → 调用 3.7.2。

#### 3.7.2 GitHub 回调绑定 `POST /auth/github/callback`

- 鉴权：需要登录
- Content-Type：`application/json`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| code | string | ✅ | GitHub 授权码 |
| state | string | ✅ | 与 authorize 返回的 state 一致 |

请求示例：

```json
{ "code": "gho_xxx", "state": "abc123" }
```

响应：无 body（绑定成功即 200）。

> 后端行为：校验 state → 用 code 换 access_token → 拉取 GitHub 用户 → 落库 `user_social`。
> - 该 GitHub 已绑定其他用户 → `50002 操作失败`。
> - 当前用户已绑定其他 GitHub → `50002`。
> - 重复绑定同一 GitHub（本人）→ 幂等成功（不再落库）。
> 一个 GitHub 只能绑一个用户，一个用户只能绑一个 GitHub（唯一索引保证）。

#### 3.7.3 解绑 GitHub `DELETE /auth/github/unbind`

- 鉴权：需要登录（从 `RefreshToken` 长 token 解析 userId）

响应：无 body（解绑成功即 200）。

## 4. 附录

### 4.1 数据模型速览（联调参考）

| 表 | 关键字段 |
|---|---|
| `user` | id(bigint PK)、username(唯一)、password(BCrypt)、status(1正常/0禁用)、create_time、update_time |
| `user_profile` | id、user_id(必填)、nickname、email、phone、avatar、bio、create_time、update_time |
| `user_role` | id、user_id(必填)、roles(JSON数组)、permissions(JSON数组)、create_time、update_time |
| `user_restrict` | id、restrict_request(限流次数)、window_second(窗口秒) |
| `user_social` | id、user_id、provider('github')、provider_uid、provider_login、created_time（provider+provider_uid 唯一、user_id+provider 唯一） |

种子数据：`admin`（角色 ADMIN+USER）/`zhangsan`（USER）/`lisi`（GUEST）；`user_restrict` 1 号配置 = 100 次 / 60 秒。

### 4.2 后端技术栈（了解即可）

Spring Boot 4.1.1（WebMVC）、Spring Security 7.0.6、MyBatis-Plus 3.5.17、jjwt 0.12.6、Redis（3 实例分库）、MinIO（对象存储）、BCryptPasswordEncoder(12)、Java 21。

### 4.3 已知风险与建议

1. `updateUserProfile` 无 `@RequestBody`，表单绑定方式对前端不友好——**建议后端补 `@RequestBody` 并改回 JSON**（当前文档按现状标注）。
2. GitHub 绑定接口中 `authorize` 返回裸 URL（非 R 包装）、`callback`/`unbind` 返回空 body，前端封装时注意区分。
3. 登录返回的 Map key 依赖后端 `token` 配置（`refresh=RefreshToken`、`generation=Authorization`），若后端改名需同步前端。
4. 列表接口为 POST + 嵌套 `pageDTO`，与常见 GET 分页不同，前端封装时注意。
